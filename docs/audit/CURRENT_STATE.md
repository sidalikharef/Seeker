## 1. Executive Summary

SEEKER is currently an **empty VS Code extension scaffold**, not an AI coding agent.

The repository contains one 11-line TypeScript source file that registers a single command and displays a notification. There is no model client, no provider abstraction, no webview, no agent loop, no tool system, no context engine, no permission system, no tests, no linting, and no CI.

The only functional behavior is a "Hello World" notification, and that behavior is **currently unreachable through the declared extension command** because the command ID in `package.json` does not match the command ID registered in `src/extension.ts`.

The repository is a clean starting point. There is no working functionality worth preserving beyond the TypeScript/VS Code scaffold itself. The existing `PHASES.md` is a useful early intent document but describes a different, DeepSeek-specific product and must be superseded by the new roadmap.

## 4. What Is Broken

### 4.1 Command ID mismatch (blocking)

- `package.json:17` contributes `"command": "Seeker.hello"`.
- `src/extension.ts:4` registers `"deepcode.hello"`.

Consequences:

- The Command Palette entry `Seeker: Hello World` will fail with `command 'Seeker.hello' not found`.
- The original `PHASES.md` instructions and README use the `deepcode` identity, which is no longer consistent with the manifest.
- The scaffold's only user-facing feature is therefore non-functional.

## 6. Architectural Assessment

### 6.1 Preservable decisions

1. **TypeScript strict mode** (`tsconfig.json:9`) — keep.
2. **CommonJS output** — compatible with the VS Code extension host; keep for the MVP unless a bundler migration is justified.
3. **`out/` as compiled output** — acceptable; keep `main` pointed at `out/extension.js` until a bundler is introduced.
4. **Minimal dependency footprint** — keep. Do not add the OpenAI SDK, LangChain, or a vector database before they are required.
5. **Single-package layout** — appropriate for the MVP. Do not create a monorepo until the agent core must run outside VS Code.

### 6.2 Constraints that will block future work

- The current source layout (`src/extension.ts` only) cannot host provider adapters, tools, and the agent loop without modularization.
- The manifest and code use two different product identities (`Seeker` vs `deepcode`), so command IDs, configuration keys, secret keys, and telemetry identifiers are undefined.
- There is no interface boundary between the VS Code host and the future agent core; adding it later without planning would couple the agent to `vscode`.
- There is no dependency policy, so provider SDKs could leak into core logic.

## 10. Recommended Migration Strategy

1. **Do not rewrite.** Keep `tsconfig.json`, `.gitignore`, and the activation entry point.
2. **Fix the scaffold in Phase 01**: unify the product identity as `seeker` (lowercase command prefix `seeker.*`), fix the command mismatch, add a launch configuration, add test/lint scripts, and commit the lockfile.
3. **Keep a single package** for the MVP. Create internal module boundaries under `src/`:
   - `src/core/` — agent loop, state, events, verification
   - `src/providers/` — provider interface and adapters
   - `src/router/` — model registry, routing, quota
   - `src/tools/` — tool definitions and implementations
   - `src/context/` — repository scanning and retrieval
   - `src/security/` — permissions, path guards, redaction
   - `src/extension/` — VS Code host integration and webview
4. **Extract to `packages/*` only when** a CLI or second host is actually being built, or when module-boundary tests require it.
5. **Implement providers in order**: OpenRouter, Groq, Gemini, then optional Mistral. Hugging Face and Cerebras are not free-tier defaults; see [PROVIDER_MATRIX.md](../providers/PROVIDER_MATRIX.md).
6. **Reach the MVP through Phases 01–07 plus a minimal slice of Phase 10**, then harden.
